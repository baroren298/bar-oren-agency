# Asset Management Architecture (CMS-wide)

Status: architecture review, pre-Sprint-1. No code, no implementation, no sprint plan.

Scope: this document designs the **permanent Asset Management layer** for the CMS — not "Gallery Upload." Gallery, talent profile photo, podcast image, homepage assets, brand logos, and future CMS modules all consume this layer.

Grounded in the current schema (`prisma/schema.prisma`) and stack as they exist today:

- Next.js (App Router), deployed on Vercel.
- Prisma + Postgres as the only database.
- `next.config.mjs` already configures `images: { formats: ['image/avif', 'image/webp'] }` — Next.js Image Optimization is already in play.
- An `ImageAsset` model already exists: `id`, `blobUrl`, `width`, `height`, `mimeType`, `sizeBytes`, `uploadedById`/`uploadedBy`, `uploadedAt`, `status` (`LifecycleStatus`), `deletedAt`, `deletedBy`. It is referenced by `TalentGalleryImage.imageAssetId`, `TalentVersion.profileImageAssetId`, and `TalentVersion.podcastImageAssetId`.
- `LifecycleStatus` already has `ACTIVE | HIDDEN | ARCHIVED | DELETED`, and soft-delete (`deletedAt`/`deletedBy`, never hard delete) is already the house style for every other model.
- Today there is no storage SDK installed and no provider env vars set — the field name `blobUrl` is generic, not tied to a vendor. This is a real asset: the schema does not yet lock you into a provider.
- Auth model is currently Owner-only, schema is Editor-ready (`Role` enum), single admin team — this is a small, trusted-uploader CMS, not a multi-tenant public-upload platform. That fact should shape every security and scale decision below; over-engineering for adversarial-public-upload threat models would be wasted effort here.

## 1. Storage provider comparison

The right frame is not "which is the best product" — it's "which storage model fits an agency CMS that today does images, and will later do PDFs, documents, and video, while living on Vercel/Next.js/Prisma for years." Evaluated against that:

**Cloudinary.** Cloudinary is an image/video-specific media pipeline: upload, on-the-fly transformation via URL parameters, and a CDN, bundled together. For pure image work it has the best developer experience and the richest transformation story (crops, focal-point-aware resizing, format negotiation, watermarking) of the three, and integrates with Next.js fairly easily via `next-cloudinary` or hand-rolled URL building. It does not integrate with Prisma at all — Prisma only ever stores the returned URL/public ID, same as any provider. The problem for this project specifically is twofold. First, Cloudinary's pricing and product surface are built around images and video; PDFs and general documents (a confirmed future module) are an awkward fit and typically end up living somewhere else, which means you'd run two storage providers in parallel rather than one. Second, going through Cloudinary couples every served image URL to Cloudinary's transformation syntax — but this project already gets format negotiation (AVIF/WebP) and resizing for free from Next.js Image Optimization, so Cloudinary's signature feature is partially redundant with infrastructure already in `next.config.mjs`.

**Vercel Blob.** The lowest-friction option for a Vercel-hosted Next.js app: no separate vendor account, deploy-key-scoped access, trivial SDK, and it composes naturally with `next/image`. For a small agency CMS at current scale, cost is a non-issue. The drawbacks are about the project's 5–10 year horizon, not today: it is a newer product with a smaller ecosystem and feature set than S3, it has no native transformation pipeline (you'd rely entirely on Next.js Image Optimization, which is fine for images but does nothing for video transcoding when that module arrives), and it ties storage to the Vercel platform — if hosting ever moves off Vercel, storage moves with it. That last point matters because "future growth" was explicitly named as an evaluation axis.

**AWS S3 (+ CloudFront, or S3-compatible like Cloudflare R2).** The most "boring" option, and that is the recommendation here precisely because it is boring. S3 is a general-purpose object store: it has no opinion about whether the bytes are a JPEG, a PDF, or an MP4, which matters once Documents and Videos ship. It is the cheapest of the three at real scale (storage is commodity-priced, egress is the main cost lever and is controllable with a CDN in front). It is platform-independent — it does not care whether the app is hosted on Vercel, a VPS, or anywhere else, which directly de-risks the "what if we leave Vercel" question. The cost is upfront developer experience: you have to wire up your own CDN (CloudFront, or R2 + Cloudflare, which has no egress fee and is the more attractive S3-compatible alternative for this exact reason), your own signed-upload flow, and you get zero built-in transformations — you'd transform via Next.js Image Optimization for images (already configured) and a dedicated step (e.g., a transcoding job) for video later.

**Recommendation for this project:** treat storage as **S3-compatible object storage (S3 or Cloudflare R2) as the system of record**, with **Next.js Image Optimization as the transformation/CDN layer for images**, which is already half-built in `next.config.mjs`. Do not adopt Cloudinary — its core value proposition overlaps with infrastructure you already have, and its product shape doesn't extend cleanly to PDFs and video. Vercel Blob is a legitimate "ship Sprint 1 today" shortcut if you want zero infrastructure setup, and it is **not a wrong choice** — but make that choice consciously as a short-term convenience, not the permanent answer, because of the platform-coupling risk. The schema already protects you here: `blobUrl` is a flat string, not a provider-specific identifier, so switching the underlying provider later is a data-migration problem (re-upload bytes, rewrite the URL column), not a schema or application-logic rewrite. This is discussed further in Section 6.

On the specific sub-questions: replacing and deleting images are an application-logic concern, not a provider feature, and are addressed in Section 2 regardless of provider. Version history of the *file bytes themselves* (as opposed to which version of a Talent points at which file) is not something any of the three providers should be asked to manage — that responsibility belongs to `ImageAsset` rows, not the storage layer (Section 2). Performance is dominated by CDN placement in front of whichever store is chosen, not by which of the three vendors is selected.

## 2. ImageAsset lifecycle

The existing schema already encodes the right answer to the hardest question here, so this section makes that design explicit rather than inventing a new one.

**Should profile image, podcast image, and gallery image point to the same `ImageAsset` model?** Yes — and the schema already does this (`TalentVersion.profileImageAssetId`, `TalentVersion.podcastImageAssetId`, `TalentGalleryImage.imageAssetId` all point at `ImageAsset`). Keep this. A single canonical asset table is what makes one upload endpoint, one storage abstraction, and one orphan-detection sweep possible across every current and future module. The alternative — a separate image table per module — would mean reimplementing upload, validation, and cleanup logic per module, which is the exact "Gallery Upload" framing this review is meant to avoid.

**Should deleting a gallery image delete the `ImageAsset`?** No, and not because of caution alone — it's structurally wrong given how this CMS is versioned. `TalentVersion` and `TalentGalleryImage` keep historical rows via `basedOnVersionId`/`basedOnRevisions` for rollback and audit. A "deleted" gallery image is really: the *current* published/draft version no longer references that `ImageAsset`, but a *superseded* historical version still does. Hard-deleting the `ImageAsset` (or its file) the moment a gallery entry is removed would silently corrupt the ability to roll back to that historical version, and would orphan the `AuditLog` row that references it. Deleting a gallery image should only ever delete (soft-delete) the `TalentGalleryImage` row, never cascade into the `ImageAsset` it points to.

**Should `ImageAsset` be archived?** Yes, using the `LifecycleStatus` enum it already has. An asset moves `ACTIVE → ARCHIVED` when it is no longer referenced by any *current* (live: draft/proposed/published) version of anything, but it should not move to `ARCHIVED` the instant the last live reference disappears — there should be a grace window (see orphan detection below) so an accidental unpublish-then-republish doesn't churn the asset's lifecycle. `DELETED` (with `deletedAt`/`deletedBy` populated, consistent with every other model in this schema) is reserved for assets that are confirmed unused after that grace window, and "deleted" still means the row and underlying blob persist for some retention period before a separate, deliberate hard-purge job removes the bytes — never an instant cascade delete triggered by a content edit.

**Should it have reference counting?** A live boolean/derived count, not a stored counter column. Because of the `basedOnRevisions` versioning chain, "reference count" is ambiguous unless you specify *which* kind of reference: total historical references (never goes to zero for any asset that was ever published, by design — that's the audit trail working correctly) versus *live* references (referenced by a version row that is currently `DRAFT`, `PROPOSED`, or `PUBLISHED`, not `REJECTED`/`SUPERSEDED`). Store nothing — compute "is this asset live-referenced anywhere" as a query at sweep time (`galleryUses`, `profileUseOf`, `podcastUseOf`, plus whatever future modules add) rather than maintaining a denormalized counter that can drift out of sync with the versioning tables it would have to mirror.

**Should orphan detection exist?** Yes, as a scheduled sweep, not a synchronous side effect of every content edit. Two distinct orphan classes need different handling: (1) assets uploaded but never attached to anything (an upload happened, the draft was abandoned) — these are the cheapest to clean up and have no audit-trail implications, since nothing was ever published referencing them; (2) assets that *were* referenced but no live version references them anymore — these need the grace window described above before archival, specifically to protect rollback and audit history. A nightly or weekly sweep job that flags class (1) for fast deletion and class (2) for archival (with hard-delete only after a longer retention window, e.g. 90 days) is the right shape — never delete synchronously inside the request that edited the content.

## 3. Upload API architecture

**One shared endpoint** — `POST /api/admin/assets/upload` — used by every module (gallery, profile, podcast, homepage, logos, and future modules), not a route per module.

The case for a single route: every module needs the identical sequence of steps — authenticate, authorize, validate mime type and size, write bytes to the storage provider, create one `ImageAsset` row, return its id and URL. A per-module route (`/api/admin/gallery/upload`, `/api/admin/talent/upload`, ...) would duplicate that sequence verbatim in N places, and any future change (switching storage providers, tightening validation, adding virus scanning) becomes an N-file change instead of a one-file change. It also matches the schema decision in Section 2: since every module attaches to the same `ImageAsset` table, having every module upload through the same code path that creates those rows is the natural mirror of that data model. A single endpoint also gives you exactly one place to enforce rate limiting and quota policy CMS-wide (Section 4), rather than reasoning about N independently-rate-limited routes.

The case *against* a single route, for completeness: different modules can have legitimately different constraints — a brand logo might require SVG support and a tighter size cap than a gallery photo; a future "documents" module needs entirely different mime types (PDF) than images. A single endpoint has to take a `purpose`/`module` parameter (e.g. `gallery`, `profile`, `podcast`, `logo`, `homepage`) and branch its validation rules on it internally, which adds a small amount of conditional logic to one file rather than eliminating it — it doesn't disappear, it just moves and gets centralized.

The recommendation is the shared endpoint with a required `purpose` (or `module`) parameter that selects a validation profile (allowed mime types, max size) from a small server-side config map. This gets the maintainability of one code path while still letting logos accept SVG and gallery images not, without forking the endpoint. The endpoint's only job is: validate → store bytes → create `ImageAsset` row → return `{ id, url, width, height }`. It must **not** know about `TalentGalleryImage`, `TalentVersion`, or any other consuming model — attaching the returned `ImageAsset.id` to a gallery slot or a profile field is the calling module's job, done in its own existing Draft/Propose/Approve flow. This keeps the upload endpoint genuinely module-agnostic rather than secretly gallery-shaped.

## 4. Security

**Allowed mime types.** Enforce server-side from a fixed allowlist per `purpose` (Section 3), never trust the client-supplied `Content-Type` header — sniff actual file bytes (magic-number / signature check) server-side before accepting. For the image-only purposes in scope now: `image/jpeg`, `image/png`, `image/webp`, and optionally `image/avif`; allow `image/svg+xml` only for the `logo` purpose, and only after sanitization (raw SVG can carry embedded `<script>`/event-handler payloads — strip or sandbox-render, never serve user-uploaded SVG as-is with script execution rights on your domain). Do not pre-build the allowlist for PDF/video now (Section 5 covers why), but do build the validation layer as a per-purpose config map so adding `application/pdf` later is a config change, not a new code path.

**Max file size.** Enforce server-side (framework body-size limits are not a substitute for an explicit check), with a per-purpose ceiling — a brand logo or profile photo has no legitimate reason to be tens of megabytes; a reasonable starting ceiling for images is in the single-digit megabytes, set deliberately low rather than "whatever the platform allows," since tightening later is a breaking change for any in-flight uploads/clients while loosening later is free.

**Virus considerations.** Given the current threat model (a small, authenticated, trusted admin team uploading their own assets — not public/anonymous upload), full antivirus scanning (e.g. ClamAV, or a paid scanning API) is reasonable to defer rather than build for Sprint 1, but the decision to defer it should be explicit and revisited the moment any upload path becomes reachable by a non-admin role or external partner. What should ship now regardless: strict mime allowlisting plus byte-signature verification (Section above) closes the most common abuse vector (disguised executables/scripts) even without a dedicated scanner, and storing uploads under non-executable, randomly-generated object keys (never the original filename) on a separate domain/subdomain from the app prevents stored files from ever being interpreted as same-origin script.

**Authorization.** Reuse the existing Role model (`Role` enum — currently Owner-only, Editor-ready) rather than inventing upload-specific permissions: only authenticated Owner/Editor sessions may call the upload endpoint, enforced by the same middleware already gating the rest of `/api/admin/*`. There is no end-user-facing upload surface in this CMS's design, and that should be a stated constraint, not an oversight — if a future module needs public or client-submitted uploads (e.g. a talent self-service portal), treat that as a new, separately-threat-modeled feature, not an extension of this admin endpoint.

**Ownership.** `ImageAsset.uploadedById` already captures who uploaded a given asset (existing FK to `User`) — keep this as the durable ownership record regardless of which module later attaches the asset. Ownership of the *attachment* (which gallery, which talent) is already tracked by the consuming model's own `createdById`/`approvedById` pattern (`TalentGalleryImage`, `TalentVersion`) — don't duplicate that on `ImageAsset` itself, since one asset can be attached by a different actor than the one who uploaded it (e.g. an Editor uploads, an Owner approves the gallery entry).

**Rate limiting.** Apply at the shared upload endpoint (Section 3's strongest practical argument for keeping it singular: one place to rate-limit). A small admin team has a naturally low upload volume, so the limit's purpose is abuse/bug containment (a runaway script, a compromised session, a buggy retry loop) rather than capacity protection — a per-user, per-minute cap is sufficient; there is no need for sophisticated adaptive rate limiting at this scale.

## 5. Future modules

Assumed future modules: Homepage banners, Brand logos, Documents, PDFs, Videos.

**Would today's `ImageAsset` model still work?** Partially, and the gap is conceptual, not cosmetic: `ImageAsset` is named and shaped for images specifically (`width`, `height` are image-only concepts; the name itself says "Image"). Documents/PDFs don't have width/height in the same sense (a PDF has page count, not pixel dimensions); video has dimensions but also duration, bitrate, and a transcoding/thumbnail-generation pipeline that an image never needs. Bolting all of that onto one ever-growing `ImageAsset` table (nullable `pageCount`, nullable `durationSeconds`, nullable `thumbnailAssetId`, ...) is the path of least resistance today and the path to a model nobody can reason about in two years.

**What should change before upload code is written:** generalize the model from `ImageAsset` to a generic `Asset` (or `MediaAsset`) record holding the fields every file type shares — id, storage URL, mime type, size, uploader, timestamps, `LifecycleStatus` — and move type-specific fields into either (a) a `kind`/`assetType` discriminator column plus a small set of nullable type-specific columns (acceptable if the type-specific field count stays small), or (b) one-to-one extension tables (`ImageAssetDetail { width, height }`, `VideoAssetDetail { durationSeconds, thumbnailAssetId }`, `DocumentAssetDetail { pageCount }`) if the type-specific surface grows. Given this schema's existing style (it already prefers dedicated columns over JSON blobs — see the podcast block comment in `TalentVersion` — and dedicated models over generic polymorphism in most places, while using a generic `Entity`/`EntityVersion` pair only where it already needed one), the discriminator-column approach is more consistent with the codebase's conventions than introducing per-type extension tables, as long as the type-specific column count stays under control.

This rename is a schema migration plus a search-and-replace of every FK name (`profileImageAssetId` could stay as-is semantically, or be renamed for consistency — a judgment call, not an architectural one), and it is far cheaper to do **before** any upload endpoint, validation config, or admin UI is built against the name `ImageAsset` than after. This is the single highest-leverage decision in this entire review to make before Sprint 1.

## 6. Risks — decisions that are expensive to change later

In rough order of how expensive they get if deferred:

**The asset model's name and shape (`ImageAsset` vs. a generic `Asset`).** Covered in Section 5. Cheap to fix now (a migration + renames, before any dependent code exists); expensive later (every upload route, validation config, and admin UI component would need to be touched once Documents/Video force the generalization anyway).

**Whether there is one upload endpoint or one per module.** Covered in Section 3. Starting with N module-specific routes and later consolidating them means rewriting N call sites in the admin UI; starting with one shared, `purpose`-parameterized route and never needing to split it is the safe default, and splitting one route into several later (if a module turns out to need a genuinely different upload mechanism — e.g. chunked upload for large video) is a much smaller change than the reverse.

**Storage provider lock-in.** Covered in Section 1. Mitigated by keeping `blobUrl` a flat, provider-agnostic string (already true) and never leaking provider-specific identifiers (Cloudinary public IDs, Vercel Blob pathnames with provider semantics baked in) into any other table or into client-side code. As long as that discipline holds, switching providers later is a backend-only, data-migration-shaped problem, not a schema or frontend rewrite. The trap to avoid: letting a transformation feature (e.g. Cloudinary's URL-based crop syntax) leak into stored data or templates, since that's what actually creates hard vendor lock-in, not the choice of object store itself.

**Whether deletion is ever hard/synchronous.** Covered in Section 2. The existing house style (soft-delete everywhere, `deletedAt`/`deletedBy`, never hard delete from request-handling code) already protects this, and the temptation to special-case "but surely it's fine to just delete the file when someone removes a gallery image" is the most likely place a future engineer breaks rollback/audit guarantees without realizing it. Document the grace-window/sweep-job design (Section 2) explicitly so that temptation has a documented answer to point to instead of being re-litigated ad hoc.

**Reference counting via a stored column instead of a computed sweep.** Covered in Section 2. A stored counter is easy to add and very easy to let drift out of sync with the actual versioning tables (a missed decrement on one of N FK relations is silent and only surfaces as "this asset got deleted while still in use," which is a production incident, not a code review catch). Computing liveness at sweep time avoids the drift class of bug entirely; this is cheap to decide now and annoying to retrofit once a stored counter is already load-bearing somewhere.

**Mime-type/size validation living in one place vs. scattered per-module checks.** Covered in Sections 3–4. If validation logic gets duplicated across module-specific code before a shared endpoint exists, consolidating it later means finding and reconciling every divergent copy (which is exactly how allowlists silently drift inconsistent between modules).

## 7. Final recommendation

A single generic `Asset` model (renamed now, before upload code exists, from today's `ImageAsset`) with a `kind` discriminator and a small set of type-specific nullable columns, carrying the fields every module already needs: storage URL, mime type, size, uploader, timestamps, and the existing `LifecycleStatus` lifecycle (`ACTIVE → ARCHIVED → DELETED`, soft-delete only, consistent with every other model in this schema). Every module — gallery, profile, podcast, homepage, logos, and future documents/video — references this one table by foreign key, exactly as `TalentGalleryImage` and `TalentVersion` already do, and never owns a duplicate per-module asset table.

One shared upload endpoint, `POST /api/admin/assets/upload`, parameterized by a `purpose` field that selects a server-side validation profile (allowed mime types, max size) per module. The endpoint's only responsibility is validate → store → create the `Asset` row → return its id; attaching that id to a gallery slot, a profile field, or a homepage banner stays entirely inside each module's existing Draft/Propose/Approve/Publish flow, which this design touches not at all.

Storage on S3-compatible object storage (S3 or Cloudflare R2) as the durable system of record, fronted by Next.js Image Optimization (already partially configured) for image transformation and CDN delivery, with Vercel Blob acceptable as a deliberate, documented short-term substitute if zero-infrastructure setup is wanted for Sprint 1 — never Cloudinary, whose value proposition this stack mostly already has and whose product shape doesn't extend to the confirmed future modules.

Deletion is always soft and always asynchronous: removing an attachment never cascades into the asset; a scheduled sweep distinguishes never-attached orphans (deleted promptly) from formerly-attached, now-unreferenced assets (archived, then hard-deleted only after a retention window), preserving the rollback and audit guarantees the rest of this schema already depends on. Reference liveness is computed at sweep time from the existing relations, never stored as a counter.

Security rides on the authorization system this CMS already has (Owner/Editor roles gating `/api/admin/*`) rather than a new permission system; mime allowlisting is enforced by byte-signature, not by trusting client headers; virus scanning is explicitly deferred given the trusted-admin-only threat model, with that deferral re-examined the day any upload path becomes reachable by a non-admin actor.

This is the version of the design built to still make sense after Documents and Video ship, without a rewrite — which was the actual brief.
