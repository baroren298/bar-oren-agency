# `components/admin/`

Admin-only UI components (Admin Panel Architecture v1.2, Section 7). Kept deliberately separate from `components/{home,about,contact,talent,layout,common,ui}/**` so admin-only code never gets bundled into the public site, and so the public component tree stays untouched and reusable for Live Preview later (Phase 8) — Live Preview renders the *real* public components against proposed data rather than a separate mockup tree, so this folder is for admin chrome (proposal diff views, dual-state panels, approval controls, etc.), not duplicates of public talent/page components.

**Admin Design System Foundation sprint added** the first six reusable components, plus a shared token file:

- `admin-tokens.module.css` — a `.tokens` CSS-module class carrying the admin palette/spacing as custom properties (mirrors `app/admin/admin-shell.module.css`'s tokens but is independent from it). Each component below composes `.tokens` on its own root element so it renders correctly even outside `<AdminShell>`.
- `PageHeader.jsx` — page title + optional description + optional right-aligned action slot.
- `Card.jsx` — generic bordered surface panel, optional heading.
- `PrimaryButton.jsx` — solid accent-colored button/link for the main action on a page.
- `SecondaryButton.jsx` — outlined, lower-emphasis button/link.
- `StatusBadge.jsx` — small color-coded pill for a status/lifecycle label (`tone`: neutral/success/warning/info/danger). Carries no business logic about what a status means — the caller decides the tone.
- `EmptyState.jsx` — simple "nothing here yet" placeholder with optional action.

Each is a plain presentational component (no `"use client"`, no hooks) so it can be rendered from Server Components — every admin page today is one — or Client Components alike. None of them touch auth, Prisma, or routing; they are pure UI. Demonstrated so far only on `app/admin/page.jsx` (the Dashboard); intended to be reused as-is by Talent, Proposals, SEO, Media, Settings, and any other admin page added later per `ADMIN_PANEL_PLAN.md`.

**Editing Experience Foundation sprint added** `ComparisonView.jsx` (+ `ComparisonView.module.css`) — the reusable Current Published / Proposed Update layout that is the foundation of the admin's whole editing philosophy ("never edit the live site directly"). Unlike the six components above, this one *is* a Client Component (`"use client"`): it needs local state to hold in-progress edits to the "Proposed Update" column. It is entity-agnostic — it takes only `fields: { key, label, value, type }[]` (`type`: `"text" | "textarea" | "list" | "boolean"`) and renders a read-only published block and an editable proposed block seeded from the same values. No save/submit, no diffing, no validation, no API calls — edits live in component state only and are lost on navigation, per this sprint's explicit "no save logic yet" scope. First used by `app/admin/talent/[id]/page.jsx` for the פרטים section; meant to be reused unchanged for Gallery, SEO, Social links, Homepage, About, Contact, and Footer editing in later sprints — each caller just supplies its own field mapping, same pattern as `buildDetailsFields()` in that page.

**Editing Experience UX Polish sprint restyled** `ComparisonView.jsx`/`.module.css` after a user review found the original version "technically correct but not obvious enough." No props, architecture, or logic changed — purely presentation: the published block now sits unboxed directly on the page background with quiet typography (an icon+eyebrow label, "🌍 גרסה מפורסמת", plus a one-line "this is what visitors see" subtitle) so it can never be mistaken for something editable; the proposed block now sits on its own soft tinted, slightly elevated surface (no heavy border — background contrast + a faint shadow do the work) with its own icon+eyebrow ("✏️ עדכון מוצע") and reassuring copy that nothing publishes until approved. The old arrow divider between the two sections is gone — a deliberately large gap plus the background contrast now carries that separation instead. Each proposed field row also gained a `.changeDot` — a small, currently inert/low-opacity dot reserved next to the field label as visual groundwork for a future real "this field changed" indicator; it does not compare values or run any diffing logic today, it only exists so a later sprint can light it up without a layout change.
